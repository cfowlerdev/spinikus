# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Spinikus is a Rust, self-hosted PaaS (a lighter Coolify/Dokploy, "self-hosted Vercel"). It is early: `spinikus-core` (domain types, IDs, deployment state machine) and `spinikus-store` (SQLite repositories, migrations, envelope encryption) cover the data model in the design doc, except backups and integrations (storage destinations, notification channels, Git connections), which come with their features, `spinikus-control` has the start of the service layer (`Control`: first-run setup, sign-in, sessions and API token authentication, `ControlError` with stable codes, projects, environments and services with permission checks and audit entries, service sources, variables (`variables.rs`), volumes (`volumes.rs`), one-click databases (`databases.rs`), domains, instance settings (`settings.rs`), deployments and the runner that drives them and the servers' route tables (`deployments/`), HTTPS certificates from ACME (`certificates/`), servers with join tokens, the internal CA (`ca.rs`) and agent enrollment, and the agent listener (`agents/`: mutual TLS, `Enroll`, `RenewCertificate`, `Connect`, `OpenSession`)), `spinikus-api` serves the JSON API under `/api/v1` and inbound Git webhooks under `/hooks` (setup, login for an API token, `me`, projects, environments, services, their source, deploy key and webhook, variables on all three scopes (with `reveal`), volumes, databases (`POST /environments/{id}/databases`), domains, deployments, their logs and SSE streams, a service's runtime logs, rollback, instance settings, servers and their enrollment tokens), `spinikus-proto` defines the agent protocol (`proto/spinikus/agent/v1/agent.proto`, compiled by `protox` in `build.rs`, so no `protoc` is needed), `spinikus-agent` enrolls (`join`, pinning the CA fingerprint), keeps the control stream open (`run`: hello, heartbeats, reconnect with backoff, certificate renewal), reports the containers Spinikus manages through the container runtime (Docker via bollard), runs `PrepareDeployment` (images: pull, pin by digest; Git: clone and build with BuildKit, `build.rs`), `StartDeployment` (with the health check), `StopDeployment`, `RemoveDeployment` (containers, then images via `ContainerRuntime::remove_image`, skipping images in use) and `RestartInstance`, serves log tail sessions (`sessions.rs`), and applies route tables, certificates and ACME challenges to its proxy, with no release commands yet, `spinikus-proxy` is the reverse proxy (route lookup, forwarding, WebSocket upgrades, HTTPS by SNI, ACME HTTP-01 answers, the HTTP-to-HTTPS redirect), and the `spinikus` binary has the CLI, config and startup. `spinikus-web` is still a `cargo new` placeholder. The design is in `docs/spinikus.md` — read it before building any feature; it records decisions (with the alternatives that were rejected) that the code is expected to follow.

### Service layer conventions

`spinikus-control`'s `Control` is the one entry point for the API, web UI, CLI and webhooks: input validation, permission checks (via `Principal::role_in` / `is_instance_admin`) and audit entries (`Control::audit`) happen there, not in the store or the HTTP layers. Errors are `ControlError`; never expose `Internal` details to clients.

- Load access with `Control::access(principal)` and check it with `Access::check_project` / `check_environment`. Something the principal has no role in is `NotFound` (existence is not revealed); something they can see without the needed role is `Forbidden`.
- Roles: instance admins create projects; project admins update and delete them and create and delete environments; environment admins rename environments; developers create and edit services; admins delete them; viewers read.
- Operations take raw input (`NewProject`, `ProjectChanges`, …), validate it (`input::name`, `input::slug`, which derives a slug from the name when none is given), and record an audit entry with `Control::audit_by` (`audit::changed` lists updated fields, never values).
- Lists return `Page<T>` (`has_more`; the next cursor is the last item's ID), with limits clamped to `page::MAX_PAGE_SIZE`.

### Agent connections

`spinikus-control::agents` implements `AgentService` as `AgentGrpc`, served by `agents::serve` over TLS with optional client certificates. The internal CA (`ca.rs`, created on first use and stored in `certificate_authority`, its key sealed under the master key) issues the listener's certificate on every start, for the fixed name `CONTROL_PLANE_SERVER_NAME`, and agents' client certificates, whose subject CN is the server ID (only the CSR's public key is used). The `identify` interceptor turns a verified client certificate into an `AgentIdentity` request extension; that is the only source of an agent's server ID, never IDs inside messages. Without one only `Enroll` works, which takes a single-use join token (`spj_…`, 1 hour); a malformed CSR is rejected before the token is used up. Revoking a server disconnects its agent and refuses its reconnects, renewals and unused join tokens. Tests in `agents/tests.rs` set the identity with an interceptor over plain gRPC; `agents/tls_tests.rs` go through the real TLS listener. `Control::agents()` is the `AgentHub`: the connected agents and a channel to each control stream (`send`, `disconnect`). Connection starts and ends hold `AgentHub::transition()` across the registry change and the database write, so a reconnect is never overwritten by the old connection's disconnect. Proto-to-core conversions live in `agents/convert.rs`, on the control side, never in `spinikus-proto`.

### Deployments

`Control::create_deployment` snapshots the service's source and config, resolves its variables (then `resolve_references`, below), and fixes its server: the service's `server_id` (placement), else the embedded server (`find_embedded_server`). Runtime settings (`port`, `start`, `healthcheck`, `shutdown_timeout`) are the `runtime` object of the service config, parsed by `spinikus_core::runtime::RuntimeSettings` (same shape as `spinikus.json`, durations like `"10s"`, unknown fields rejected), and checked when a service is saved and when it is deployed. The runner (`deployments/runner.rs`, `Control::run_deployments`, spawned by `server run`) is the only thing that moves deployments forward: each pass lists active deployments, starts at most one per service, fails those whose agent is lost or whose phase timed out (both counted from the runner's start at the earliest), and sends the next command. Command IDs are `<deployment ID>/<step>` (`prepare`, `start`, `stop`, `cleanup`; `commands.rs`), so results map back to a deployment, and only the deployment's own server may report on it. `sent` remembers unanswered commands to resend after `resend_after` and drops a server's entries when its agent reconnects (`agent_connected`); hold its lock across a pass or a result so they never interleave. Results and progress arrive through `deployment_result` / `deployment_progress` from the agent listener. Failure messages go on the deployment event (`message`). Timings are `DeploymentTimings` (`Control::with_deployment_timings` in tests). Prepare results may carry the repository's `spinikus.json` (`PreparedImage.app_file`): `with_app_file` merges it into the snapshot through `spinikus_core::app_file::AppFile` (`from_file` lists the fields it set) and `record_build` stores it, or the deployment fails with `build_failed`. Git sources over SSH get a deploy key (`sources.rs`: created with the source, rotated by `create_deploy_key`, sealed in `deploy_keys`), sent in the prepare command. Progress from the deployment's own server goes to its log (`deployments/logs.rs`: `<log dir>/deployments/<id>.log`, `==> phase` lines, capped at `MAX_LOG_SIZE`; `server run` uses `<data_dir>/logs` via `Control::with_log_dir`, tests have none unless they set one). `Control::rollback_service` (`POST /services/{id}/rollback`, optional `{ "deployment_id" }`, default the newest superseded deployment still kept) creates a `rollback` deployment with the target's snapshot, image, commit and variables on the target's server; the runner starts it at `starting`. Only superseded, uncleaned deployments on a non-revoked server can be targets. Each runner pass ends with `clean_up_deployments` (`deployments/cleanup.rs`): `to_clean` (pure) keeps active deployments, the newest `releases_kept` superseded ones (setting, default 5), failed or canceled ones newer than the last that went live (at most `FAILURES_KEPT`), and targets of rollbacks in progress; the rest get a `RemoveDeployment` (step `remove`) with the image references to remove: none while a kept deployment on that server runs the same image, else every deployment's own reference to it (`image_tag` for builds, the pinned reference for pulls; rollbacks have none) and the image itself. The result sets `cleaned_at` (`mark_deployment_cleaned`); a revoked server's deployments are only marked. Failures and cancels end the log with `==> failed (<reason>): …` / `==> canceled` (`log_line`). Git webhooks (`webhooks.rs`, one per service with a Git source, table `webhooks`, secret sealed with the webhook ID as context, `whk_` IDs): `create_webhook` makes one or replaces its secret (the ID, so the URL, stays; the secret is returned only then), and `receive_push(provider, id, PushDelivery)` checks the signature (`signed`: HMAC-SHA256 for GitHub's `sha256=` and Gitea's hex, GitLab's token compared by digest; `Unauthenticated` otherwise), parses the payload with `spinikus_core::webhook::Push`, and queues a `git_push` deployment of the pushed commit through `queue_deployment` (shared with `create_deployment`) with `Actor::Webhook` — unless it is a ping, not a push, another branch, a tag, a deleted branch, a push that changed nothing under the root directory (`Push::touches`; unknown change lists count as changes), or a commit already in progress or live, which are `PushOutcome::Ignored` with the reason. Each delivery's result goes in `last_delivery`. `Control::follow_deployment(principal, id, offset)` (`deployments/stream.rs`) streams `DeploymentUpdate`s: the log's complete lines after a byte offset (woken by `DeploymentLogs.appended`, a broadcast sent on every append), the status when it changes (checked every `STATUS_INTERVAL`), and `End` once the deployment is live or finished; the API's `GET /deployments/{id}/stream` turns them into SSE `log` (ID = offset, so `Last-Event-ID` resumes), `status` and `end` events. Runtime logs come from the agent on demand (`service_logs.rs`): `Control::service_logs` finds the container of the live (or named) deployment, registers a pending session (`Sessions`), sends `OpenSession` with a `LogTailSession` on the control stream (command ID `session/<id>`, not tracked by the runner), and waits up to `SESSION_OPEN_TIMEOUT` for the agent's `OpenSession` stream, which `attach_session` matches by its first frame's session ID and server; frames become `ContainerLogUpdate`s, and dropping the returned stream closes the session. `GET /services/{id}/logs` (`?deployment_id=&since=&tail=&follow=`, tail default 100, `MAX_TAIL`) serves them as SSE `log` and `end` events. Variables (`variables.rs`): developers of a scope (project, environment or service; `scope_with_access`) create, update and delete its variables, viewers list them (secret values are `None`), and `reveal_variable` needs the scope's admin role and is audited (`variable.reveal`); a secret can't be made plain again; values are at most `MAX_VALUE_LEN`, without NUL. A value may contain references, `${{ <service slug>.<NAME> }}` (`spinikus_core::reference::Template`; `$${{` is a literal), checked for syntax when saved and resolved by `resolve_references` when a deployment is queued: the named service of the same environment (`find_service_by_slug`; the service itself included) and the variable it gets, its value taken as is (references in it are not followed), and the result is secret if any referenced value is; a reference to nothing is `Invalid` on `variables`. Volumes (`volumes.rs`): developers create and update them (`name` a slug, `mount_path` a `MountPath`), admins delete them; changes apply at the next deployment, and a service with volumes is deployed with `recreate`. Their data stays on the server when deleted. `start_command` puts every container on its environment's network (`commands::network_name`: `spinikus-<environment ID>`) with the service's slug as its alias (`ServiceNetwork` in `StartDeployment`), so services reach each other by slug, and runs `RuntimeSettings::command()` (`start` through `/bin/sh -c`, else the image's command) as `StartDeployment.command`. Databases (`databases.rs`): `create_database` builds a `database` service from `spinikus_core::database::DatabaseSpec` (`Engine::Postgres` 15–18, `Engine::Redis` 7–8, newest by default; the official image by major version, a `data` volume at the image's data path, config `{ database: { engine, version }, runtime }`, and generated variables: `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`/`DATABASE_URL` or `REDIS_PASSWORD`/`REDIS_URL`, the password and URLs secret), each part through the normal operations (`create_service`, `create_source`, `create_volume`, `create_variable`), then queues its first deployment; if a later part fails the service is deleted. Redis starts with `--requirepass "$REDIS_PASSWORD" --appendonly yes`. Not done yet: release commands, pruning the BuildKit cache, preview deployments for pull requests.

### Routes and the proxy

`deployments/routes.rs` builds every non-revoked server's route table (`build_routes`) from live app deployments with a port: each custom domain of the service (a redirect for domains with `redirect_to`), plus its generated hostname from `spinikus_core::route::generated_hostnames` (`<service>-<environment>-<project>.<base_domain>`; the `base_domain` setting defaults to `localhost`, `null` turns them off, and custom domains under it are refused). Each runner pass calls `sync_routes` first: the store's `save_route_table` keeps the revision when the routes are unchanged and otherwise gives one at least the current time in milliseconds, and an unapplied table goes to the agent as `SetRoutes` (`routes_sent` dedups like `sent`). The agent's `SnapshotApplied` and the `routes_revision` in `Hello` call `routes_applied`, which counts only the current revision. A draining deployment gets its stop only once its server's table is applied and no longer targets it. Settings are one resource per key (`GET`/`PUT /settings/{key}`, revision 0 and `If-Match: "0"` for a key never set); only known keys exist. On the agent, `proxy.rs` saves tables to `routes.json`, loads them on start so the proxy serves before the control plane answers, and resolves a deployment's running container to its loopback endpoint through the runtime (`RuntimeUpstreams`, cached until a connect fails). `RunOptions::proxy` takes the bound listeners (`ProxyListeners`: HTTP, and HTTPS if any); the binary binds `[proxy] listen` and `https_listen` (defaults `0.0.0.0:80` and `:443`; the repo's `spinikus.toml` uses `127.0.0.1:8000` and `:8444`) unless `[proxy] enabled = false`. `spinikus-proxy` knows only core route and certificate types and the `Upstreams` trait, and its tests run against a local backend.

### Certificates

`spinikus-control::certificates` gets HTTPS certificates once the `acme_email` setting is set (`acme_directory_url` defaults to Let's Encrypt). `Control::run_certificates` (spawned by `server run`, woken when routes are sent or settings change) orders one certificate per public, non-wildcard routed hostname (`Hostname::is_public`) through the `AcmeClient` trait (`acme.rs`: `InstantAcme`, the real client; tests use a fake via `Control::with_acme_client`), renews at two thirds of the lifetime, and records failures with backoff in `hostname_certificates` (store: `record_certificate_issued`, `record_certificate_failure`). HTTP-01 challenges (`challenges.rs`) go to every connected agent as an `AcmeChallenges` snapshot, in memory only, resent on connect; publishing waits up to `challenge_wait` for the agents' `SnapshotApplied`. `sync_routes` ends with `sync_certificates`: each server's unexpired certificates for its routed hostnames are stored as `server_certificates` (revisions like route tables) and sent as `SetCertificates` with their keys (`certificates().sent` dedups); `Hello.certificates_revision` and `SnapshotApplied` record what the agent has. On the agent, `proxy.rs` (`ProxyState`) saves certificates to `certificates.json` (mode 0600) and loads them on start. The proxy answers `/.well-known/acme-challenge/` over HTTP for any host with exactly the key authorization, and redirects HTTP to HTTPS (308) for hosts it has a certificate for. The Pebble test is `#[ignore]`d (`orders_a_certificate_from_pebble`, see its comment).

### Agent side

`spinikus-agent` keeps its state in `<data_dir>/agent` (`agent.json`: URL, server ID, CA; `identity.json`: certificate and key, mode 0600), each file replaced atomically. Joining first does a TLS handshake that accepts the control plane only if its chain contains a CA with the pinned fingerprint that signed the listener's certificate (so the listener sends the CA in its chain), then enrolls over normal TLS with that CA as the only root. The agent always verifies the control plane as `CONTROL_PLANE_SERVER_NAME`. `run` returns an error only for what retrying cannot fix (not enrolled, revoked, certificate expired, unsupported protocol); everything else reconnects with `Backoff`. The container runtime is the `runtime::ContainerRuntime` trait: `DockerRuntime` (bollard; `DOCKER_HOST`, else `/var/run/docker.sock`, else Docker Desktop's `~/.docker/run/docker.sock`, connecting lazily so a stopped daemon is `RuntimeError::Unavailable` rather than fatal) and `MemoryRuntime` for tests (behind the `test-support` feature, which the binary's dev-dependencies enable). Managed containers are those labeled `spinikus.service` and `spinikus.deployment` (`SERVICE_LABEL`, `DEPLOYMENT_LABEL`), plus `spinikus.port` for the app port. The app port is published on `127.0.0.1` with a runtime-picked host port (`ContainerRuntime::endpoint`); the health check and the proxy connect there, never to container IPs (see the design doc). `ContainerSpec::network` (`Network`: name and aliases) joins the container to a network, which `DockerRuntime::create` creates first if missing (a bridge labeled `spinikus.network`; `ensure_network`); the agent accepts only names starting with `spinikus-` and slug aliases (`deploy.rs`). Empty networks are not removed yet. A deployment has one container, named `spinikus-<deployment ID>`, so a repeated `StartDeployment` reuses it; containers get the `unless-stopped` restart policy, and one that fails verification is stopped but kept for its logs until the control plane cleans the deployment up. The health check (`health.rs`) is a hand-written HTTP/1.1 `GET` (2xx/3xx passes; failures in the start period don't count); without a path the container only has to keep running through the start period. Deployment handlers live in `deploy.rs`; Git builds in `build.rs` (`BuildOptions`: a per-deployment work dir under `builds/`, `known_hosts`, and `local_repositories`, which `RunOptions` sets only in tests): the `git` CLI with no user config, `spinikus.json` from the root directory, `spinikus_core::build::BuildSettings` (Dockerfile only so far), paths kept inside the repository, then `ContainerRuntime::build` (BuildKit; `.git` left out of the context; tagged `spinikus/<service>:<deployment>`, run by image ID). Build variables are build args; secret ones are redacted from progress lines (`Progress::redact`). commands report phases and log lines with `Progress` (best effort, dropped while disconnected), and `Commands::next` always yields a command's progress before its result. The reporter (`report.rs`) sends a full `StateReport` after `Welcome` only from a successful listing (a full report replaces the server's instances, so never send one while the runtime is unreachable), then a delta per runtime event, and resyncs with a new full report after the runtime fails. Commands (`commands.rs`) run in their own tasks, outlive reconnects (results go out on the next connection; running IDs go in `Hello`), and are idempotent by ID: a running ID is ignored, a finished one gets its stored result. They are kept in memory only so far. Commands the agent cannot run yet get a failed `CommandResult` right away. `OpenSession` is not a command for `Commands`: `connection.rs` hands it to `sessions::open`, which opens the session stream (first frame: the session ID) and serves a log tail from `ContainerRuntime::logs` (`LogOptions`: `since`, `tail`, `follow`; Docker's frames are split into timed lines; `MemoryRuntime::write_log` in tests) until the log ends or the control plane closes its side; it then ends its own side and waits for the control plane's (`CLOSE_GRACE`), since dropping the call would discard unsent frames. Runtime log lines are not redacted. Tests that need Docker are `#[ignore]`d (`cargo test -p spinikus-agent --test docker -- --ignored`, and `cargo test -p spinikus --test agent -- --ignored` for deployments, from an image and built from Git, and for databases, through a real control plane and agent). `crates/spinikus/tests/https.rs` gets a certificate from a fake CA that checks the challenge through the real proxy. The embedded agent (`crates/spinikus/src/embedded.rs`) is this machine's agent on single-server installs: `server run` gets or creates the one `embedded` server, enrolls it with a system-issued join token through the real `join` over loopback (re-enrolling if its files are for another server or CA), and runs it in-process over loopback mTLS; it does not run if its server is revoked. On shutdown the agent listener closes agents' streams (`AgentHub::disconnect_all`) so it can drain, with a 5-second grace period, and on start it marks every server disconnected. `AgentHub::disconnect` only signals the connection to stop; its reader unregisters it and records the disconnect. Tests that need both a control plane and an agent live in `crates/spinikus/tests/` (shared setup in `tests/common`, whose `ControlPlane` runs the deployment runner too), since only the binary may depend on both.

### API conventions

`spinikus-api` handlers stay thin: extract, call one `Control` method, shape the response. Use the crate's own extractors (`Body`, `Path`, `Query`, `Authenticated`, `IfMatch`, `Client` in `extract.rs`) rather than axum's, so every rejection is a problem detail (`ApiError`, `application/problem+json` with a stable `code`). Request bodies are API-specific structs with `deny_unknown_fields`; responses serialize the core types. Single resources return their revision as `ETag` (`response::tagged`/`created`), updates require it in `If-Match` (428 without, 412 if stale), and lists use `PageParams`/`PageBody` (`?after=&limit=`, `next_cursor`). Authentication is bearer API tokens only; session cookies belong to the web UI. Inbound webhooks (`routes/hooks.rs`, `POST /hooks/git/{provider}/{id}`, providers `github`, `gitlab`, `gitea`/`forgejo`) are authenticated by their signature instead, answer `202` with the deployment or `200` with why nothing deployed, and take bodies up to `MAX_DELIVERY_SIZE`. Tests in `crates/spinikus-api/tests/` drive the router with `tower::ServiceExt::oneshot`.

### Store conventions

Each entity gets a repository trait in `spinikus-store` (methods named after the entity, e.g. `create_project`, since `SqliteStore` implements them all) with:
- soft delete (`deleted_at`) for projects, environments, services and domains, with slugs and hostnames unique only among non-deleted rows; creating under a deleted parent is `NotFound`, deleting a parent with active children is `HasChildren`;
- a `revision` column bumped on every user-facing update, and updates that take the expected revision (`RevisionMismatch` otherwise);
- cursor pagination by ID; IDs come from a process-wide monotonic ULID generator, so they sort in creation order;
- multi-statement writes in `SqliteStore::begin_write` (`BEGIN IMMEDIATE`), and timestamps written from Rust via `db::format_timestamp`;
- SQL as `&'static str` only (sqlx 0.9 rejects dynamic strings): when a query varies, build each variant with `concat!` and a small macro (see `columns!`, `insert_under!` in `variables.rs`) rather than `format!`;
- input validation (slugs aside) left to the service layer; the store keeps rows consistent with `CHECK` constraints and unique indexes.
- secrets sealed with `SqliteStore::keyring()` (`secrets.rs`): envelope encryption with XChaCha20-Poly1305, data keys in `data_keys` wrapped by the master key. Store the `Sealed` key ID next to the ciphertext, and pass the owning row's ID as the `context` so a ciphertext can't be moved to another row.

## Commands

```sh
cargo build                          # build the whole workspace
cargo check --workspace
cargo test --workspace               # all tests
cargo test -p spinikus-core          # one crate
cargo test -p spinikus-core it_works # one test by name filter
cargo run -- server run              # start the control plane (applies migrations, serves the API on [http] listen, default 127.0.0.1:8080, agents on [agents] listen, default 0.0.0.0:8443, and the embedded agent unless [agents] embedded = false, with its proxy on [proxy] listen and https_listen)
cargo run -- server migrate          # apply pending migrations and exit
cargo run -- admin create-user --email you@example.com --name You   # first admin; password from SPINIKUS_ADMIN_PASSWORD or a prompt
SPINIKUS_JOIN_TOKEN=spj_… cargo run -- agent join https://host:8443 --ca-fingerprint sha256:…   # enroll this machine's agent (token and fingerprint from POST /api/v1/servers/{id}/enrollment-tokens)
cargo run -- agent run               # run the agent; state in <data_dir>/agent
cargo clippy --workspace && cargo fmt
```

Formatting is plain `cargo fmt` on stable, configured by `rustfmt.toml` (stable options only; don't add nightly-only ones such as `trailing_comma`).

The binary loads `spinikus.toml` from the **current working directory** (required), overlaid by env vars with prefix `SPINIKUS` and `__` as the nesting separator (e.g. `SPINIKUS_LOGGING__LEVEL=info`). `RUST_LOG` overrides `logging.level` when set. Run it from the repo root. The database defaults to `<data_dir>/spinikus.db` (`data/` in dev, gitignored). The master encryption key comes from `SPINIKUS_SECRETS__MASTER_KEY` or `[secrets] master_key_file`; with neither, `<data_dir>/master.key` is generated on first start. `server run` refuses to start if the database's data keys were wrapped by a different master key.

Migrations live in `crates/spinikus-store/migrations/` as `NNNN_<name>.sql`, are embedded with `sqlx::migrate!`, and run automatically on startup. Tables are `STRICT`; timestamps are `TEXT` in UTC RFC 3339 with milliseconds (`strftime('%Y-%m-%dT%H:%M:%fZ', 'now')`).

Planned but not yet present (per the design doc): `rust-toolchain.toml`, `deny.toml`, `[workspace.lints]`, cargo-nextest, and an `xtask` crate for OpenAPI generation, asset builds and releases — use `xtask` rather than shell scripts for dev chores once it exists.

## Architecture

One binary, two runtime roles:
- **Control plane** owns state and decisions: service layer, reconciler (desired state in DB vs. state reported by agents), durable deployment state machine, job queue, internal CA/enrollment, SSE event stream.
- **Agent** owns containers, builds and traffic on one server: runtime driver (bollard), builder (Dockerfile/Compose via runtime, Railpack for auto-detect), hyper+rustls proxy with ACME, reporter.

Agents **dial out** to the control plane over a long-lived mTLS gRPC stream (`spinikus.agent.v1`, tonic/prost); the control plane never calls into an agent. On single-server installs the agent runs in-process but still connects over loopback gRPC — there is one code path, don't add an in-process shortcut.

### Crate dependency rules (enforced by crate boundaries — keep them)

| Crate | Role | Internal deps |
| --- | --- | --- |
| `spinikus-proto` | `.proto` + generated code | none |
| `spinikus-core` | domain types, prefixed ULID IDs, deployment state machine as pure logic, `spinikus.json`/`spinikus.toml` schemas; **no I/O** | none |
| `spinikus-store` | repository traits, SQLite (sqlx) impl, migrations, envelope encryption | core |
| `spinikus-control` | control plane (see above) | core, store, proto |
| `spinikus-api` | Axum JSON API under `/api/v1`, auth, OpenAPI | control |
| `spinikus-web` | Maud + HTMX (SSE) UI, embedded vendored assets | control |
| `spinikus-proxy` | proxy, route table, SNI resolver, ACME | core |
| `spinikus-agent` | runtime trait, builder, command handlers, local persistence | core, proto, proxy |
| `spinikus` | binary: clap CLI, hand-written API client, wiring | all |

- `api` and `web` never depend on each other; both are thin layers over the shared service layer in `control`, so the UI can never do something the API can't.
- `agent` and `control` never depend on each other; they share only `proto`.
- `proxy` knows only route/certificate types.
- Planned Cargo features `server` and `agent` (both default) to allow a slim agent-only build later.

Internal crates are referenced via `[workspace.dependencies]` (`spinikus-core.workspace = true`).

### Key design invariants

- `spinikus.toml` is instance config only (data dir/DB, listen addresses, log level, master key source). Everything else lives in the database and is managed via API/UI.
- Per-repo `spinikus.json` holds only settings that change with the code version (build, runtime, health check, env var *names*, cron, monorepo `apps`). Never domains, secret values, placement or credentials. When it sets a field, the file wins over the DB.
- Desired state and observed state live in separate tables; agents write only observed state.
- Deployments are immutable records with a config snapshot. States: `queued → preparing → releasing → starting → verifying → live → draining → superseded`, plus terminal `failed` (with reason code) and `canceled`. Each transition writes a deployment-event row in the same transaction. Rollback = new deployment reusing an old image + snapshot, starting at `starting`.
- IDs are prefixed ULIDs (`svc_…`, `srv_…`); cursor pagination uses the ID.
- Secrets: envelope-encrypted with a key ID per value; master key lives outside the DB. API secrets are write-only.
- API conventions: RFC 9457 problem details with stable `code`, `Idempotency-Key` on side-effecting POSTs, `If-Match` revisions on updates, additive-only changes within `v1`.
